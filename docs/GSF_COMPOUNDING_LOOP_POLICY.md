## 1. 원칙 (Joseph 확정 · 2026-07-17)

**반복 작업의 산출물에는 개선 루프를 내장한다. 인간의 수정·결정은 버려지지 않고 기록되어, 다음 산출물의 입력(에이전트 훈련 데이터)이 된다. 별도의 "프로세스 개선 논의"는 열지 않는다 — 작업을 하는 것이 곧 개선이다.**

네 개의 하위 원칙:

1. **빈 페이지 금지**: 에이전트는 인간에게 백지를 주지 않는다. 모든 반복 산출물은 "생성해 달라"가 아니라 **채택/수정/기각할 수 있는 준비된 선택지** 형태로 제시한다. 인간의 에너지는 생성이 아니라 판단과 (그 사람만 가진) 경험·맥락 주입에만 쓰인다.
2. **수정 = 데이터**: 인간이 에이전트 산출물을 고친 내역은 지정된 축적처에 기록된다. 고침 자체가 다음 산출물의 기준이 된다.
3. **환류 의무**: 에이전트는 다음 산출물 생성 시 축적처를 반드시 참조한다 — 같은 수정을 두 번 받으면 루프 고장이다.
4. **졸업 기준**: 수정량이 0에 수렴한 작업은 완전 위임(에이전트 자율)으로 전환한다. 루프의 목적은 영원한 검수가 아니라 **위임의 확대**다.

**근거**: 프로세스 개선을 별도 회의·문서 개정으로 하면 ① 개선 비용이 실행 시간을 잠식하고(과설계) ② 개선 내용이 실제 작업과 괴리된다. 개선을 산출물 안에 내장하면 비용이 0에 수렴하고, 개선이 항상 실전 데이터에서 나온다. 복리 구조: 매주의 작은 수정이 축적처에 쌓여 에이전트 산출물의 출발선을 계속 끌어올린다 — 작업량은 같아도 품질이 우상향한다.

**실증 사례 (2026-07-17, 촉발점 — GSFArk 주간 브리프 체제)**: 에이전트가 title 2안·H2 후보·도입 골격을 준비 → Joseph이 채택/수정(월 15–20분) → 수정 사례가 `SEO_WRITING_GUIDE §2` 표에 축적 → 다음 주 초안이 그 사례를 반영 → 수정량 주간 감소 → 수렴 시 AG 완전 이관. 여기에 외부 권위 루프(승리 쿼리 → GSC 인접 쿼리 → 다음 소재로 자동 환류)가 겹쳐 이중 플라이휠이 된다.

## 2. 하드게이트 규격

### 2.1 발동 조건 (이때는 반드시)

- **반복 작업을 에이전트에 위임하는 프로세스의 신규 설계/대개정** (주간·월간 루프, 정기 산출물, 배치 작업)
- 기존 반복 프로세스에서 **같은 유형의 수정이 2회 이상 반복**됐을 때 — 단, 1차 응답은 **프로세스 대개정이 아니라** 아래 §2.1.1

#### 2.1.1 "같은 수정 2회" — Cursor 잠금 해석 (과민 방지)

| 단계 | 동작 |
|---|---|
| **1차 (필수)** | 에이전트 **자진 보고** + 축적처 미기입·환류 누락 여부 점검 + 해당 사례 1행 기입 |
| **2차 (조건부)** | 루프가 **아예 없거나**, 축적·환류가 있는데도 **같은 유형이 3회째**면 §2.3 4항으로 프로세스 보강 |

"같은 유형" = **지시·패턴 수준의 반복** (예: title 전방 명사 누락, 경험 디테일 요청이 막연함). 오타·날짜·슬러그 1회성 교정은 카운트하지 않는다.

### 2.2 면제 (루프가 없는 곳에 루프를 강제하지 않는다 — 과설계 방지)

- **1회성 작업** (단발 분석·마이그레이션·수리) — 축적할 다음 회차가 없다
- **탐색 단계** (아직 반복 형태가 확정되지 않은 실험) — 루프 설계는 반복이 확정된 뒤에
- 이미 기계적 게이트가 담당하는 것 (lint·validate·CI — 이건 코드가 축적처)
- **§F 잠금 문서 자체의 1회 개정** — D-004 외부 검증과 동일하게, 본 게이트는 **반복 프로세스 문서**에만 적용 (전략 1회성 잠금에 루프 4항 강제 금지)

### 2.3 게이트 규격 — 반복 프로세스 문서의 필수 4항

반복 작업 프로세스 문서는 아래 4항 없이 잠금(§F) 불가:

| # | 항목 | 답해야 할 질문 |
|---|---|---|
| 1 | **준비 원칙** | 에이전트가 무엇을 어디까지 준비해 오는가? 인간의 작업이 채택/수정/주입 형태인가? (백지 시작 항목 = 0) |
| 2 | **축적처** | 인간의 수정·결정 사례가 **어느 파일**에 쌓이는가? (예: WRITING_GUIDE §2 표, 원장 비고란, 프로젝트별 LEARNINGS.md) |
| 3 | **환류 규칙** | 다음 산출물 생성 시 축적처를 어떻게 참조하는가? (에이전트 지시문에 축적처 경로 명시) |
| 4 | **졸업 기준** | 수정량이 어느 수준에 수렴하면 완전 위임하는가? 위임 후 스팟체크 주기는? |

### 2.4 운영 (누가 무엇을)

- **에이전트 (Claude/AG)**: 산출물을 선택지 형태로 준비 · 수정 사례를 축적처에 기입 · 생성 전 축적처 참조. **같은 수정을 2회 받으면 자진 보고** (§2.1.1)
- **Cursor**: §F 잠금 시 **반복 프로세스 문서**에 "§2.3 4항 존재" 확인 (D-004 외부 검증 게이트와 **병렬** — 해당되면 둘 다). 축적처가 실제로 쌓이는지 스팟체크 (빈 축적처 = 루프 미작동)
- **Joseph**: 수정할 때 "왜"를 한 줄 남기면 축적 효율 배가 (선택 사항 — 강제 아님). 판단 필요 항목만 보고받음

### 2.5 건강 지표 (회고 시점에만 — 주간 측정 금지)

- **수정량 추이**: 회차당 인간 수정 건수가 감소하는가 (감소 없으면 축적처·환류 설계 재점검)
- **위임 전환 수**: 졸업한 작업이 늘어나는가
- 측정 시점: 각 프로젝트의 기존 회고 주기에 통합 (신규 회의체 신설 금지)
